PART C/D — CREATE A DEPLOYMENT

1. How many Pods were created?
   3
1. What is the name of the Deployment?
   web-app
1. What image are the Pods using?
   nginx:latest
1. What is the difference between the Pod you created earlier and the
   Pods created by the Deployment?
   The standalone Pod (nginx-pod) is unmanaged — if it crashes or is
   deleted, nothing replaces it. The Pods created by the Deployment are
   managed by a ReplicaSet, which automatically detects if a Pod goes
   missing and creates a new one to maintain the desired count.
1. Why would we use a Deployment instead of creating individual Pods
   manually?
   A Deployment provides self-healing, easy scaling (one command changes
   the replica count), and rolling updates, all handled automatically.
   Managing individual Pods by hand would require manually tracking each
   one, recreating failed Pods, and updating them one at a time.

PART E — SCALE THE DEPLOYMENT

1. How many Pods existed before scaling?
   3
1. How many existed after scaling to 5?
   5
1. How many existed after scaling down to 2?
   2
1. What command did you use to scale the Deployment?
   kubectl scale deployment web-app –replicas=5
   kubectl scale deployment web-app –replicas=2
1. Why is scaling a Deployment easier than manually creating additional
   Pods?
   A single command updates the desired replica count, and Kubernetes
   automatically creates or terminates Pods to match it. There’s no need
   to manually track Pod names, recreate failed instances, or update
   each one individually.

PART F — DEMONSTRATE KUBERNETES SELF-HEALING

1. What happened when you deleted the Pod?
   The Pod was terminated, and within seconds Kubernetes automatically
   created a brand-new Pod (with a new name and IP) to replace it.
1. How many Pods did you have after Kubernetes finished creating the
   replacement?
   2
1. Did you manually create the new Pod?
   No
1. Why did Kubernetes create a replacement Pod?
   The ReplicaSet continuously compares the actual number of running
   Pods to the desired number (2). Deleting a Pod created a mismatch,
   which the ReplicaSet immediately corrected by creating a new Pod.
1. What Kubernetes concept does this demonstrate?
   Self-healing / desired-state reconciliation. Kubernetes constantly
   works to keep the real cluster state matching the state that was
   declared.

PART H — TROUBLESHOOTING CHALLENGE

1. What status are the new Pods showing?
   ErrImagePull or ImagePullBackOff
1. What error can you find in the Pod events?
   Kubernetes reports it could not pull the image “nginx:invalid”
   because that tag does not exist in the image registry (manifest
   unknown / not found).
1. Why can’t Kubernetes successfully start the container?
   The specified image tag doesn’t exist in the registry, so there is
   nothing for Kubernetes to download and run the container from.
1. How would you fix the problem?
   Change the image back to a valid tag (nginx:latest) in
   deployment.yaml and re-apply it with:
   kubectl apply -f deployment.yaml.
